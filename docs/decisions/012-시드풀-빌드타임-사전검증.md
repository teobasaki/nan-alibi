# ADR 012 — 사건 시드를 빌드 타임에 미리 검증해 굽는다

## 맥락
`generateValidCase(seed, maxAttempts = 40)` 가 **게임 시작 시점**에 돌았다.
검증에 실패하면 파생 시드로 최대 40회 재생성하므로, 최악의 경우 첫 화면이 지연된다.
완료기준 D4 는 이 비용을 빌드 타임으로 옮길 것을 요구한다.

## 측정
시드 1~3000 스캔 결과 **첫 시도 통과율 100.0% (3000/3000)**.
시드당 생성+검증 약 0.65ms (400시드 재검증 403ms).
즉 지금 생성기는 사실상 실패하지 않지만, 그 사실이 **보장**은 아니었다 —
풀은 그 보장을 데이터로 못 박는다(런타임 재시도 0회).

## 결정
- `npm run gen:pool` (`scripts/gen-pool.mjs`) 이 시드를 스캔해 `src/data/pool.json` 에 굽는다.
  엔진이 TS 라 노드에서 직접 못 부르므로 `scripts/review.mjs` 와 같이 임시 테스트를
  vitest 러너에 태운다. 단 결과는 stdout 이 아니라 파일로 받는다(대용량 stdout 절단 전례).
- `src/data/pool.ts` 가 `pickPoolSeed(rnd: number): number` 하나만 노출한다.
- **저장하는 값은 시드 그 자체다.** `functions/api/interrogate.ts` 가 같은 시드로 사건을
  재생성하므로, 시드를 가공하거나 사건 데이터를 구우면 클라이언트와 서버가 갈라진다.
- `tests/pool.test.ts` 가 풀의 **모든** 시드를 `maxAttempts=1` 로 재검증한다.

## 버린 대안
- **통과한 3000개를 전부 굽기**: 통과율이 100% 라 `pool.json` 이 그대로 `[1..3000]` 이 된다 —
  정보량 0 인 15KB 를 번들에 싣는 꼴. 400개로 캡하되 **스캔 범위 전체에 고르게**(7 간격) 뽑았다.
  앞에서 400개를 자르면 1~400 구간만 회귀 감시하게 되기 때문이다.
- **사건 객체(CaseFile) 자체를 굽기**: 생성 비용은 더 줄지만 서버와의 시드 계약이 깨지고,
  생성기를 고칠 때마다 구운 데이터가 조용히 낡는다.
- **런타임 유지 + maxAttempts 축소**: 지연을 줄일 뿐 없애지 못하고, 실패 시 예외로 게임이 멈춘다.

## 남은 것
`src/main.ts` 배선(시드 선택을 `pickPoolSeed` 로 교체)은 이 작업 범위 밖 — 동시 작업 충돌 회피.
`?seed=` URL 파라미터로 들어온 임의 시드는 여전히 재시도 경로를 탄다(의도됨).
