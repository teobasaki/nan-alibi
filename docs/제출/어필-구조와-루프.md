> NAN 2026 제출물 3·4번을 쓸 때 참고할 정본. 새 저장소로 옮겨 갈 문서다.
> 여기 적힌 사례는 전부 nan-alibi 에서 **실제로 일어난 일**이고, 그렇지 않은 것은 적지 않았다.

## 0. 어필의 조직 원리 — 하나만 기억하면 된다

채용 연계 심사에서 읽는 사람이 찾는 것은 **판단력의 증거**다. 도구 목록은 신호가 아니다. 누구나 쓴다.

> "Meshy 를 썼습니다" → 정보량 0
>
> "크레딧 690 중 305(44%)를 태웠고, 원인이 ① 1명으로 검증하지 않고 8명을 한꺼번에 돌린 것
> ② 도구 출력을 확인 없이 다음 단계에 먹인 것 두 가지였고, 둘 다 스크립트에 검증으로 박아
> 재발을 막았습니다" → **이게 신입과 뽑을 신입을 가른다**

**규칙: 능력 주장마다 (치른 대가 + 거기서 나온 규칙)을 붙인다. 대가 없는 주장은 빼는 게 낫다.**

### 걸러야 할 것

규정에 "무단 도용 시 선발 취소" 가 있는 문서다. 검증 안 되는 주장은 **리스크 대비 이득이 없다.**

| 주장 | 어디에 써야 하나 |
|---|---|
| Java · 백엔드 아키텍처 | 이 프로젝트는 TypeScript 다. 4번이 아니라 **5번 롤 기술서**로 |
| 로컬 kimi · 검색 API | 실제 호출 흔적 없음 — **뺀다** |
| worktree 병렬 | 설계 문서는 있으나 이 프로젝트엔 미적용 — "설계는 있으나 이번엔 미적용" 으로 정직하게 |
| Claude ↔ Codex 적대 검증 | 문서만 있고 실적용은 한 방향뿐이었다. 새 저장소에서 **양방향으로 실제로 돌린 뒤에** 쓴다 |
| BDD | 한국어 서술형 `it()` 이다. "행위 서술 테스트" 로 낮춰 적는다 |

## 1. 네 개의 구조 — 자연어 설명

한 문장으로 묶으면 이것이다.

> ## AI 가 만들게 하되, AI 가 판정하게 두지 않는다.

이 문장이 두 스케일에서 똑같이 반복된다.

- **런타임** — LLM 은 말하고, 규칙은 엔진이 갖고, 승패는 테스트가 정한다.
- **파이프라인** — AI 가 코드를 쓰고, 들어갈지는 커밋 게이트가 정한다.

아래 네 구조는 이 한 문장을 실행하는 장치다.

---

### 1-1. 테스트 구조 — 층마다 다른 속도로 다른 것을 잡는다

테스트는 한 덩어리가 아니다. **속도와 범위의 피라미드**다. 각 층은 서로 다른 종류의 오류를 서로 다른 비용으로 잡는다.

| 층 | 잡는 오류 | 비용 | 언제 돈다 |
|---|---|---|---|
| **타입 검사** (`tsc --noEmit`) | 구조 — 없는 필드, 틀린 시그니처, null 누락 | ~0.5초 | 편집 직후 |
| **단위 테스트** (vitest) | 규칙 — 계산이 틀림 | ~1.2초 | 편집 직후 |
| **시뮬레이션** (봇 플레이·시드 스캔) | 균형 — 규칙은 맞는데 게임이 성립 안 함 | 초 단위 | 규칙을 건드릴 때 |
| **브라우저 실측** | 표현 — 계산은 맞는데 화면이 틀림 | 분 단위 | UI 를 건드릴 때 |
| **사람** | 재미 — 전부 맞는데 재미없음 | 시간 단위 | 마일스톤 |

핵심 원리는 하나다.

> **아래층에서 잡을 수 있는 것을 위층에서 잡으면 낭비다.**

브라우저를 띄워야만 확인되던 것을 타입 검사가 잡게 만드는 것이 설계다. 그래서 규칙 계산을 화면에서 떼어 엔진에 둔다 — 화면 없이 검증되면 루프가 **분 단위에서 초 단위로** 내려간다.

**순서도 비용이다.** 타입 검사를 테스트보다 먼저 돌리는 이유는, 테스트가 실패하면 원인을 찾아야 하지만 타입 오류는 원인이 이미 메시지에 적혀 있기 때문이다.

**게이트로 만들어야 구조가 된다.** 통과 여부를 사람이 판단하면 바쁠 때 건너뛴다. 커밋 훅이 판단하면 못 건너뛴다.

### 1-2. 반증 구조 — 확인은 자기가 할 수 없다

**확인 편향은 노력으로 이길 수 없다. 역할로 이긴다.**

검증자에게 "맞는지 확인해줘" 라고 물으면 맞다고 답한다. 확인하려는 사람과 반증하려는 사람은 **애초에 다른 곳을 본다.** 그래서 세 가지 장치를 쓴다.

**① 역할 반전** — 임무를 뒤집어 준다.

> ✗ "이 문서가 맞는지 봐줘"
> ✓ "너는 심사위원이고, **이 팀을 떨어뜨릴 근거를 찾는 것이 임무다**"

**② 렌즈 분할** — 같은 것을 여러 명이 보면 중복이다. 각도를 갈라야 서로 다른 것을 본다.

| 렌즈 | 묻는 것 |
|---|---|
| 과장 | 저장소가 뒷받침하지 못하는 동사는? ("자동으로", "병렬로") |
| 숫자 | 문서의 모든 수치를 다시 세면 재현되는가? |
| 규정 | 제출 규정 위반 소지는? 필수 항목 누락은? |

**③ 기본값을 유죄로** — 애매할 때 어느 쪽으로 기울지를 **미리** 정한다.

> "파일:줄 근거를 못 대면 ABSENT 다. '있을 법하다' 는 ABSENT 다."

이 한 줄이 실제로 **9건을 걸러냈다.** 없었으면 전부 문서에 들어갔고 심사위원이 5분 만에 깼을 것이다.

**반증은 코드만이 아니라 문서에도 적용된다.** 실제로 자기 문서를 반증시킨 결과:

- 페르소나 프리픽스 **668자 → 실측 median 1,257자** (1.9배)
- 3D 에셋 **2.64MB → 실측 22.1MB** (8.8배)
- 제출 문서 두 개가 **커밋조차 안 됨**, 저장소 익명 404 — **실격 소지**
- 그리고 문서가 아니라 **게임의 정답 유출 버그** 1건

마지막 것이 이 구조의 값을 가장 잘 보여준다. 문서를 검증시켰는데 **제품 버그가 나왔다.**

> **자기가 쓴 것을 자기가 다시 읽으면 하나도 안 나온다.**

### 1-3. 개선 구조 — 고치는 것과 되돌아오지 못하게 하는 것은 다른 일이다

**"고쳤다" 의 정의를 먼저 고정한다.**

> 동작이 바뀌었다 ✗
> **수정 전에는 실패하고 수정 후에는 통과하는 테스트가 존재한다** ✓

수정은 3단으로 간다.

**① 증상 제거** — 눈에 보이는 것을 없앤다. **여기서 멈추면 반드시 재발한다.**

**② 원인 이동** — "왜 그 자리에서 이런 일이 가능했나" 를 묻는다. 답은 대개 **경계가 잘못 그어져 있다** 이다.

정답 유출 사례: 증상은 "폴백일 때 해금 여부가 노출된다" 였지만, 원인은 **판별이 UI 에 있었다는 것**이다. 화면이 규칙을 계산하고 있었으니 규칙이 바뀔 때 화면이 따라가지 못했다. 그래서 판별을 엔진(`presentReveal()`)으로 옮겼다 — 옮기고 나니 테스트가 가능해졌다.

**③ 고정** — 테스트로 못 박는다.

> ### 주석은 게이트가 아니다
>
> 이 사례의 진짜 교훈은 여기 있다. `game.ts` 주석에 *"조사 0회로 답이 새어나간다 — 그래서 닫았다"* 고
> **이미 적혀 있었다. 적혀 있었는데 되살아났다.** 폴백이라는 새 경로가 생기면서.
>
> 문장으로 적은 규칙은 다음 변경에서 조용히 깨진다. 테스트로 적은 규칙만 빨간불을 켠다.

#### 그리고 — 측정은 만료된다

가장 값진 교훈은 이것이다. **668자는 틀린 적이 없다. 맞았다가 만료됐다.**

ADR 을 쓰던 날엔 진짜로 668자였다. 그 뒤 프롬프트에 규칙과 조서 지시가 붙으며 1,257자로 자랐고, **아무도 다시 재지 않았다.** 그런데 "캐시를 포기한다" 는 결정 전체가 그 숫자 하나에 걸려 있었다.

> 결정은 ADR 로 남겼지만, **그 결정이 딛고 선 측정값에는 만료 감시를 걸지 않았다.**

여기서 나온 규칙:

> **결정의 근거가 되는 숫자는 문장에 적지 말고 테스트에 적는다.**
> 문장에 적힌 숫자는 늙고, 테스트에 적힌 숫자는 늙으면 빨간불이 켜진다.

성공은 운으로 설명되지만, **자기 결정이 만료된 것을 스스로 잡아낸 이야기는 운으로 설명되지 않는다.**

### 1-4. 진행 구조 — 갈 곳보다 멈출 곳을 먼저 정한다

**① 계약을 먼저 쓴다.** 네 칸이 없으면 그냥 기획서 요약본이다.

> 완료 조건 · **중단 조건** · 검증 방법 · **버린 대안**

중단 조건이 핵심이다. 대부분 성공 조건만 쓴다. **"이 조건이면 멈추고 되돌아온다" 를 미리 주는 것** — 이것이 AI 를 굴려본 사람과 아닌 사람을 가르는 자리다.

**② 모호도 게이트.** 해석이 갈리는데 그 해석들이 **서로 다른 결과**를 낳으면 멈추고 묻는다. 해석이 여럿이어도 결과가 같으면 그냥 한다. *모든* 모호함에 묻는 것은 게으름이고, *어떤* 모호함에도 묻지 않는 것은 무모함이다.

**③ 모르는 것을 먼저 찔러본다.** 도메인 무지는 반복으로 풀리지 않는다. 루프를 무작정 돌리는 대신 **최소 구현으로 한 번 찔러보고 보고받는다.** 3D 가 이 원칙을 어겨서 크레딧 44% 를 태웠다 — 1명으로 검증하지 않고 8명을 한꺼번에 돌렸다.

**④ 한 번에 한 층.** 규칙 → 테스트 → 화면 순으로 간다. 섞으면 실패했을 때 어느 층이 원인인지 갈리지 않는다.

**⑤ 결정은 버린 대안과 함께 남긴다.** 왜 안 했는지가 없으면 몇 달 뒤 같은 것을 다시 검토한다. ADR 에 "버린 대안" 칸을 **필수**로 둔 이유다.

**⑥ 교훈은 층을 타고 올라가되 상한이 있다.**

```
전역 플레이북 (상한 50)   ← 다른 분야에서도 인용 가능한가?
   ▲
도메인 플레이북 (상한 30)  ← 같은 분야 다른 프로젝트에서 인용 가능한가?
   ▲
프로젝트 ADR              ← 대부분 여기 남는다
   ▲
작업 로그 (원문)
```

**상한이 설계의 핵심이다.** 새 항목을 만들기 전에 기존 항목에 흡수되는지를 먼저 본다. 무제한으로 쌓으면 아무도 읽지 않는 목록이 되고, 읽히지 않는 규칙은 없는 규칙이다.

### 1-5. 네 구조가 하나로 닫힌다

```
   진행 구조 ──(무엇을 할지 · 언제 멈출지)──▶ 작업
       ▲                                      │
       │                                      ▼
   개선 구조 ◀──(잡힌 것)── 반증 구조 ◀── 테스트 구조(게이트)
       │                        ▲                  ▲
       └──(고정: 새 테스트·새 규칙)───────────────┘
```

테스트가 게이트를 만들고, 반증이 게이트가 못 잡는 것을 잡고, 개선이 잡힌 것을 **게이트로 내려보내고**, 진행이 다음을 정한다.

> **이 고리의 산출물은 코드가 아니다.
> 다음 판에 이 고리를 덜 돌아도 되게 만드는 규칙이다.**

## 2. 제출물 4번 문서 구조

```
§0  명제 — AI 가 만들게 하되, AI 가 판정하게 두지 않는다
      ↑ 같은 모양이 런타임과 파이프라인 두 스케일에서 반복된다. 이게 제출물의 한 문장이다.
§1  런타임 AI 아키텍처 ─ 제품 안의 AI
§2  개발 파이프라인 아키텍처 ─ 이걸 만든 AI
§3  비용·토큰 경제 ─ 숫자만
§4  실패와 복구 ─ 가장 강한 장, 가장 길게
§5  도구·API 지도 + 외부 에셋 출처 ─ 규정 필수 항목
§6  검증 체계 ─ 층별 게이트
§7  탐색 세션과 정리 세션 ─ 두 단계를 다 공개
부록 프롬프트 전문
```

**§0 이 승부처다.** 대부분의 제출물은 "AI 를 이렇게 썼습니다" 나열로 끝난다. 한 문장의 설계 원칙이 두 층에서 반복되는 것을 보이면, 그건 도구를 쓴 게 아니라 **아키텍처를 한 것**이다.

**§4 를 제일 길게 쓴다.** 성공은 운으로 설명되지만 복구는 안 된다. 사례마다 고정 3줄:

> 무엇이 잘못됐나 → 어떻게 알았나 → 무엇으로 재발을 막았나

## 3. 협업 아키텍처 — 팀원(기획·UX) ↔ 구현

산출물 사슬로 남기면 PR 코멘트보다 강하다.

```
팀원 설계 문서 ─▶ 적대 검증(렌즈 분할) ─▶ 도장 찍힌 계약서 ─▶ 구현
      ▲                                                        │
      └────────────── 구현이 설계를 반증 ◀────────────────────┘
```

**① 양방향이어야 한다.** 한 방향이면 검증이 아니라 검수다. 설계가 구현을 반증하고 구현이 설계를 반증해야 대칭이 된다.

**② 렌즈를 갈라야 한다.** 두 모델에게 같은 것을 시키면 중복이다.

| 검증자 | 렌즈 | 묻는 것 |
|---|---|---|
| Claude | 일관성 · 누락 | 서로 모순되는 문장은? 정의 안 된 용어는? |
| Codex | 구현 가능성 · 엣지 | 이대로 짜면 어디서 막히나? 명세가 침묵하는 입력은? |

**③ 계약서에 네 칸.** 완료 조건 · 중단 조건 · 검증 방법 · 버린 대안.

**④ 반증이 설계를 실제로 바꾼 기록이 남아야 한다.** 전부 통과한 리포트는 "검증한 척" 으로 읽힌다.

## 4. 어필을 숫자로 고정할 자리

| 능력 | 숫자 |
|---|---|
| 비용 관리 | Meshy 크레딧 690 중 305(44%) 낭비 → 원인 2건 → 스크립트에 검증으로 고정 |
| 검증 루프 | 테스트 136건 · 시드 400개 사전검증 100% · 런타임 재시도 0회 |
| 판단 기록 | ADR 15편 전부 **버린 대안** 포함 · 커밋 65개 |
| 프롬프트 효율 | 실작업 세션 111건, **평균 623자** |
| 자기반증 | 검증 에이전트가 자기 문서에서 낡은 숫자 3건 + **제품 버그 1건** 적발 |

마지막 두 줄이 제일 세다. **평균 623자**는 프롬프트를 길게 쓰는 능력이 아니라 **컨텍스트를 설계해 짧게 써도 되게 만든 능력**이다.

## 5. 정리 세션 프롬프트 설계

능력이 나열되면 홍보문이고, 필요해서 나오면 증거다.

| 막 | # | 지시 | 드러나는 것 |
|---|---|---|---|
| 계약 | 1 | 목표·제약·완료기준·**중단 조건**·토큰 예산·테스트 전략을 한 번에. "모호하면 구현 전에 물어라" | pre-mortem · 인간 개입을 앞으로 몰기 |
| | 2 | 스킬 인벤토리 확인 → 부족한 외부 스킬 설치 | 외부/내부 스킬 운용 |
| 설계 | 3 | "모르는 도메인부터 식별해라. 거기는 루프 대신 최소 구현으로 찔러보고 보고해라" | 비용 관리의 핵심 판단 |
| | 4 | 판정 소유권 경계 선언 — LLM 이 승패에 손대지 못하게 | 아키텍처 |
| | 5 | 서브에이전트 병렬로 대안 3안 → 적대 심사 → 채택 + **탈락안 기록** | 오케스트레이션 · 교차검증 · ADR |
| 구현 | 6 | 행위 서술 테스트 먼저 (실패하는 상태로) | 테스트 우선 |
| | 7 | 단순 변환은 저가 모델, 판정·설계는 상위 모델로 라우팅 | 비용 라우팅 |
| | 8~10 | 노드별 구현 + 각 노드마다 게이트 통과 확인 | 노드별 검증 루프 |
| | 11 | **일부러 게이트를 밟게 두고** 잡히는 것을 보인 뒤 수정 | 이탈 대응 · 복구 |
| 검증 | 12~14 | 커밋 게이트 · 배포 · 실측 | — |
| 회수 | 15~16 | 이번에 나온 규칙을 스킬·플레이북으로 승격 | **스노우볼이 눈에 보이는 자리** |

**11번을 빼면 안 된다.** 매끄러운 로그는 가드레일이 있다는 것을 증명하지 못한다. **게이트가 실제로 무언가를 막는 장면**이 한 번은 있어야 §4 가 성립한다.

## 6. 규정에서 놓치기 쉬운 것

- **제출 영상에 AI 합성·조작 불가.** *"실제 플레이 화면 그대로 담아야 합니다."*
  → 영상 생성 도구는 **게임 내 에셋**(인트로·엔딩)에만 쓰고, 그 출처는 4번 문서에 적는다.
  **제출물 2번 영상은 반드시 실제 플레이 녹화여야 한다.**
- **외부 에셋 출처·라이선스를 4번 문서에 반드시 명시.** 누락 시 선발 취소 가능.
- **저장소는 공개 권장.** 비공개면 심사 계정 초대 필요. 심사 종료까지 접근 유지.
- **팀원 롤 기술서는 2인 이상이면 필수.**
